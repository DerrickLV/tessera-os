# Build Brief — Phase 3: The numbers stop being invented

**Prerequisite:** Phases 1 and 2, both merged and serving.
**Scope:** every figure the engine emits into a memo or an agreement.
**Not in scope:** sector coverage (Phase 4), commercial terms (Phase 5).

---

## 1. The problem, stated precisely

The engine currently produces numbers that look researched and are not. Three
examples, all live:

**The ordinary-course threshold** — `governance.py:440–447`

```python
_THRESHOLD_FLOOR = 10_000
_SYNTHETIC_THRESHOLD = 50_000

def _ordinary_course_threshold(profile: VentureProfile) -> int:
    scaled = int(round(profile.initial_capital * 0.02, -3))
    return max(_THRESHOLD_FLOOR, min(scaled, 250_000))
```

Two percent of initial capital. Floor ten thousand. Cap two hundred fifty
thousand. Not one of those four numbers came from anywhere. They are a plausible
shape with invented parameters, and Phase 1 only fixed the case where capital is
zero — the other path still ships a fabricated number into a governance document
with no indication that it was guessed.

**The approval percentages** — `governance.py:533–534`

```python
return ("supermajority", 75, "scaffold")
return ("majority_with_minority_veto", 51, "scaffold")
```

75 and 51. Both invented. Both marked `scaffold`, which is honest at the
provenance layer — and both render into the memo as a specific percentage a
client will read as advice.

**Everything downstream inherits it.** The threshold appears in eight of the ten
`_BASE_RESERVED` entries by reference, in the filled agreement text, and in the
memo. One invented number propagates into a document a client may hand to
counsel.

### Why "it's marked scaffold" is not sufficient

The provenance model does its job: it records that these are not adopted Tessera
positions. What it does not do is stop a specific number from appearing in a
sentence that reads like a recommendation. A reader sees *"contracts above
$40,000"*, not *"contracts above a figure we generated by multiplying your
capital by a coefficient nobody chose."*

The fix is not better labelling. It is to stop emitting a number the system
cannot source.

## 2. Design decisions

### D1. Three states, not one

Every numeric output is exactly one of:

- **Stated** — the client gave it. Carries the intake evidence already built in
  Phase 2 (`"stated by <name>"`). Usable without qualification.
- **Proposed** — the system offers a figure *and the reasoning that produced
  it*, explicitly as a starting point requiring confirmation. Renders as a
  question, never as a settled term.
- **Unresolved** — no basis exists. Becomes a blocking open question, exactly as
  Phase 1 item 1.4 does for zero capital.

There is no fourth state where a number appears without the reader knowing which
of these it is.

### D2. A proposal must carry its derivation

A proposed number renders with the rule that produced it, in plain language:

> **Ordinary-course threshold — proposed: $40,000.**
> Derived as 2% of stated initial capital ($2,000,000), which is a common
> starting point for a two-member venture but is not a Tessera position and has
> not been tested against your actual operating budget. Confirm or replace
> before this reaches a document.

A reader who disagrees can see exactly what to argue with. A reader who accepts
it has accepted something specific.

### D3. An unconfirmed proposal cannot reach an agreement

The memo may carry proposals. `to_draft_request()` must refuse while any
proposal is unconfirmed — same mechanism as the existing unanswered-questions
guard. A number that has not been looked at by a person does not enter a
document that a person signs.

### D4. Confirmation is a recorded act, not a checkbox

Confirming a proposed number records who confirmed it and when, and moves it to
**stated** with that person as its evidence. This is the same shape as the
adoption ledger, and for the same reason: a figure in a client's operating
agreement should be traceable to a human who accepted it.

### D5. No coefficient survives without provenance

`0.02`, `10_000`, `250_000`, `75`, `51` — each either gets a documented source
and moves to a named constant with that source in the docstring, or is removed
and its output becomes a proposal with an explicit "no basis" derivation. The
second option is fine. Silently keeping them is not.

## 3. Work items

### 3.1 — A number that knows what it is

**Change.** Introduce a type carrying value, state, derivation, and evidence:

```python
NumberState = Literal["stated", "proposed", "unresolved"]

class DerivedNumber(BaseModel):
    label: str                       # "ordinary-course threshold"
    value: int | None                # None when unresolved
    state: NumberState
    derivation: str                  # plain-language rule, required for "proposed"
    confirmed_by: str = ""           # user id, set on confirmation
    confirmed_at: datetime | None = None
```

**Acceptance.**
- `state == "proposed"` with an empty `derivation` fails validation.
- `state == "unresolved"` with a non-`None` value fails validation.
- `confirmed_by` set while `state != "stated"` fails validation.
- A `DerivedNumber` never carries a `Basis` (the governance literal). Different
  concept, same trap as Phase 2's D2 — assert it in a named test.

### 3.2 — The threshold becomes a proposal

**Change.** `_ordinary_course_threshold` returns a `DerivedNumber`. With stated
capital it proposes 2% with the derivation spelled out. Without capital it is
unresolved and blocks, as Phase 1 already establishes.

**Acceptance.**
- Stated capital → `state == "proposed"`, derivation names the coefficient and
  the input.
- No capital → `state == "unresolved"`, blocking open question raised.
- The floor and cap are named constants whose docstrings say plainly that they
  are unsourced, or they are gone.
- No code path returns a bare `int` for this value.

### 3.3 — Approval percentages become proposals

**Change.** `_control_rule` returns the rule plus a `DerivedNumber` for the
percentage.

**Acceptance.**
- 75 and 51 render as proposals with derivations, not as settled terms.
- The memo's control section reads as a question where the number is proposed.
- `ControlModel.approval_threshold_percent` accepts the proposal shape;
  everything reading it handles an unconfirmed value.

### 3.4 — Confirmation, and the gate

**Change.** A console endpoint confirms a proposed number for a project; the
confirmation records user and timestamp from the authenticated context.

**Acceptance.**
- Confirming moves the number to `stated` with the confirmer as evidence.
- `to_draft_request()` raises while any number in the recommendation is
  `proposed` or `unresolved`, naming each one.
- A confirmation attempt from a user outside the project's scope is refused
  (403), same boundary as `/v1/structure/intake`.
- Confirmations survive a restart — they live in the durable store, opened
  through `sqlite_store.connect`.

### 3.5 — The memo says which is which

**Change.** `render_structure_memo` renders the three states distinguishably.

**Acceptance.**
- A stated number renders plainly with its source.
- A proposed number renders with its derivation and an explicit call to confirm.
- An unresolved number renders as an open question, never as a blank or a zero.
- A memo containing any proposal cannot report status `draft`.

### 3.6 — Sweep for the rest

**Change.** Find every remaining literal number that reaches a memo or document.
Known: `governance.py:616` (the 15% valuation band), `:620` (25/75 cash-note
split), `:896` (the 1% shotgun unit). Phase 5 owns the commercial meaning of
those; Phase 3 owns the fact that they are currently invented.

**Acceptance.**
- A test enumerates every numeric literal reaching rendered output and asserts
  each is either a `DerivedNumber` or a documented constant with a source.
- The test fails loudly when someone adds a new bare number. That is the point —
  this is a ratchet, not a one-time cleanup.

---

## 4. Invariants

1. No rendered number without a state a reader can see.
2. `DerivedNumber` never carries a `Basis`.
3. An unconfirmed number never reaches an agreement.
4. Confirmation records a person.
5. Everything from `CLAUDE.md` continues to hold — provenance, separation of
   duties, trust zones, no external actions.

---

## 5. Definition of done

- Full suite green, ruff clean, security scan clean.
- A memo generated from a real intake shows at least one proposal, with its
  derivation, and refuses to produce a document until it is confirmed.
- Confirming it in the console produces a document carrying the confirmed figure
  and naming who confirmed it.
- No bare numeric literal reaches rendered output anywhere in the codebase.
